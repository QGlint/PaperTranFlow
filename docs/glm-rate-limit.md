# GLM 限流（速率限制）应对说明

> 依据智谱官方文档：https://docs.bigmodel.cn/cn/api/rate-limit 与
> https://docs.bigmodel.cn/cn/faq/api-code
> 本文档记录 PaperTranFlow 的限流应对设计与依据，便于后续维护。

## 一、官方机制（要点）

速率限制是**并发请求数**限制（不是单纯的请求频率）：

> **并发数**指的是：同一时刻正在处理中的请求数量。

| 场景 | 说明 |
| --- | --- |
| 按用户权益等级 & 模型 | 不同模型有不同并发上限；权益等级越高额度越大 |
| 高峰期动态限流 | 账户短时间大量并发超限 → **按账户维度限流**（非永久封禁） |
| 平台级服务过载 | 模型整体访问量激增 / 底层算力高负载 / 平台维护 → 与单一账户行为无关 |

## 二、相关错误码（官方表）

| 业务码 | HTTP | 含义 | 官方建议处理 |
| --- | --- | --- | --- |
| **1302** | 429 | 账户已达速率限制 | 降低并发、**增加请求队列/排队机制** |
| **1305** | 429 | **平台服务过载** | **稍后重试**、**增加重试间隔**、避免立即高频重试 |
| 1234 | 500 | 网络错误 | 稍后重试 |
| 1200 | 500 | API 调用失败 | 可重试 |
| 1230 | 500 | API 调用流程出错 | 可重试 |
| **1301** | **400** | 内容安全审核未通过 | **重试无意义**（同一输入仍会失败） |
| 1308/1310/1316-1321 | 429 | 已达使用上限（额度耗尽） | 等额度重置，**不宜狂重试** |
| 1000-1222 | 4xx/5xx | 鉴权 / 参数 / 模型错误 | 修正请求，不重试 |

## 三、官方通用建议

> 1. **控制并发与请求频率**：使用请求队列或并发池；避免瞬时「洪峰式」请求；
>    **避免固定间隔的高频重试**
> 2. 非实时场景可通过 **Batch API / 异步请求** 降低并发压力

## 四、PaperTranFlow 的实现

### 1. 严格串行（对应「降低并发」）

`translation.concurrency` 恒为 `1`，逐个 chunk 串行翻译，无任何并发：

```text
chunk-1 → 完成 → chunk-2 → 完成 → ...
```

### 2. 请求间隔 + 抖动（对应「避免固定间隔高频重试」）

两次请求之间保持 `request_interval` 秒间隔，并叠加 ±30% 随机抖动，
打散请求节奏，降低被判定为「密集请求」的概率。

### 3. 按错误类型分级退避

| 错误 | 起步退避 | 增长 | 上限 |
| --- | --- | --- | --- |
| 1305 平台过载 | `overload_base` = 30s | 指数（×2） | `max_delay` = 300s |
| 1302 速率限制 | `rate_limit_base` = 10s | 指数（×2） | `max_delay` = 300s |
| 普通错误 / 网络 | `initial_delay` = 2s | 指数（×2） | `max_delay` = 300s |

所有退避都叠加抖动，避免多个重试「同步撞墙」。

### 4. 业务错误码优先于 HTTP 状态码（关键）

GLM 的 1302/1305 **都以 HTTP 429 返回**。若只取 HTTP 状态码，
会丢失「限流」语义、退避过短 —— 这正是早期版本持续撞墙的根因。

因此 `glm.py` 先解析响应体中的业务码（`error.code` / `code` / `msgCode`），
再决定退避策略。

### 5. 额度/内容类错误不重试

- `1308/1310/1316-1321`（额度耗尽）：重试只会浪费配额
- `1301`（内容安全）：同一输入重试必然失败

### 6. Checkpoint + 续跑（对应「排队/延迟处理」）

每个 chunk 成功后立即写 checkpoint。遇到限流中断时，用 `resume` 续跑，
已完成部分**不会重复调用** GLM。这样在平台高峰期可以「错峰」分多次跑完。

```bash
papertranflow resume input.md       # 从 checkpoint 继续
```

## 五、参数配置

`config/user.toml` 或 `config/example/user.example.toml`：

```toml
[translation]
concurrency = 1          # 严格串行（勿改）
max_retries = 5          # 单 chunk 最大重试次数
backoff_base = 2.0       # 退避指数基数
request_interval = 3.0   # 请求间最小间隔（秒）
```

## 六、高峰期实践建议

1. **分次跑**：一个 PDF 一次跑不完很正常，`resume` 即可继续
2. **避开高峰**：1305 是平台过载，换时段（如夜间）通常明显改善
3. **不要缩短退避**：调小 `rate_limit_base`/`overload_base` 只会加剧撞墙
4. 若长期不足，可参考官方「速率限制调整申请」（通用 API 用户）
